# UmJoonSIC for VS Code

SIC와 SIC/XE 실습 코드를 VS Code에서 편집하고 어셈블·링크·디버깅하는 확장입니다. 기존 엄준SIC의 Java 엔진을 보강해 포함했으며, 별도 앱이나 HTTP 서버를 실행할 필요가 없습니다.

## 설치

VS Code **1.106 이상**을 지원합니다. 실행·어셈블에 필요한 **Java 17 이상**은 기존 설치를 찾아 사용하며, 없으면 공식 Temurin JRE를 자동으로 준비합니다. 자동완성과 문법 강조는 Java 없이도 사용할 수 있습니다.

[GitHub Releases](https://github.com/guosasipo/The-UmJoonSIC/releases/latest)에서 최신 `umjoonsic-*.vsix`를 내려받아 Extensions 메뉴의 **Install from VSIX…**로 설치합니다. 탐색기에서 실습 폴더를 우클릭해 **UmJoonSIC: SIC 프로젝트 만들기**로 시작합니다. 이전 버전을 사용 중이었다면 업데이트 후 **Developer: Reload Window**를 한 번 실행합니다. Marketplace에는 아직 배포하지 않았습니다.

Java는 `JAVA_HOME`, `PATH`와 macOS Homebrew 설치 경로에서 찾습니다. 없으면 확장 전용 저장소에 Temurin 17 JRE를 내려받아 SHA-256을 검증한 뒤 설치합니다. 준비된 JRE는 오프라인에서도 재사용하며 시스템의 `PATH`나 `JAVA_HOME`은 바꾸지 않습니다. 자동 설치는 신뢰된 작업 폴더에서만 동작하고 `umjoonsic.autoInstallJava`로 끌 수 있습니다.

자동 준비가 취소되거나 실패하면 실행·어셈블 명령으로 다시 시도할 수 있습니다. 준비된 런타임이 일부 손상됐으면 새 런타임으로 복구합니다. 직접 설치한 Java는 **UmJoonSIC: Select Java Executable**로 선택합니다. 명시한 `javaPath`가 잘못된 경우 자동 설치로 대신하지 않고 오류를 표시합니다. **Java Installation Guide**는 공식 Temurin 설치 페이지를 엽니다. JRE로 확장을 사용할 수 있으며, 소스에서 엔진을 빌드할 때만 JDK가 필요합니다.

## 첫 실습

1. 탐색기에서 실습 폴더를 우클릭해 **SIC 프로젝트 만들기**를 누릅니다. 선택한 폴더에 `project.sic`과 `main.asm`을 만듭니다. 기존 asm 파일이 있으면 덮어쓰지 않고 프로젝트에 등록합니다. 이미 `.sic`이 있는 작업 폴더에는 다시 만들 수 없습니다.
2. 기존 프로젝트는 **폴더 열기**만 하면 됩니다. 루트의 `project.sic`을 자동으로 감지하고 소스 목록·모드·장치 설정을 불러옵니다. `project.sic`을 열면 **프로젝트 설정 화면**이 나타납니다. Main·실행 파일·파일 장치·SIC/SIC XE 모드·자동 진행 간격을 편집하고 **저장**합니다.
3. 코드를 입력합니다. Ctrl+Space는 자동완성, Hover는 명령 설명, F12는 라벨 정의 이동입니다.
4. 소스 편집기 상단의 **Assemble Project**는 선택한 프로젝트 폴더의 `.out`에 `.obj`·`.lst`·`.log`를 쓰고 Listing을 엽니다. 외부 소스를 포함해도 산출물 위치는 같습니다. 작업 폴더 없이 실행하는 독립 파일은 소스 옆의 `.out`을 사용합니다.
5. **Debug Project** 또는 F5는 시작 위치에서 멈추고 보조 사이드바에 **UmJoonSIC 실행** 뷰를 자동으로 엽니다. 소스 왼쪽에 중단점을 찍고 Continue·Step Into·Step Over·Step Out을 사용합니다.
6. 실행·디버깅 시 표 형태의 **Listing**이 자동으로 열립니다. 주소·기계어·라벨·명령·피연산자·주석·NIXBPE·명령 opcode 비트·데이터를 포함한 이진 코드를 표시하고 현재 PC 행을 강조합니다. 자동 진행·단계 실행·일시정지 때 현재 명령을 따라가며 필요한 경우 해당 소스 표로 전환합니다. 표 안의 파일 탭으로 소스를 전환하고, 피연산자의 기호를 누르면 정의된 행과 메모리로 이동합니다. 다른 편집기 탭을 다녀와도 선택한 파일과 행을 유지하며, 실행이 진행되거나 재시작되면 현재 PC를 따라갑니다. 표 왼쪽에서 중단점을 설정할 수 있으며, 닫은 뒤 **Show Listing**으로 다시 열어도 실행은 유지됩니다.

인식한 프로젝트 폴더 안의 `.asm`은 SIC 언어로 자동 연결합니다. 프로젝트 파일을 지우면 자동 연결을 해제합니다. 프로젝트 파일이 없는 일반 폴더의 `.asm`은 건드리지 않습니다. `*.sic.asm`은 독립 파일로도 자동 연결됩니다. 프로젝트 없이 사용할 때는 **Select SIC / SIC XE Mode** 명령 또는 다음 폴더 설정을 사용할 수 있습니다.

```json
{
  "files.associations": { "*.asm": "umjoonsic" },
  "umjoonsic.mode": "sicxe",
  "umjoonsic.stepDelayMs": 500
}
```

`J HALT` 같은 자기 점프를 종료로 판정하고 최종 메모리·레지스터를 유지합니다. 디버깅 중지는 명시적으로 Stop을 눌러 완료합니다.

## 자동 진행과 화면

실행·메모리·Listing·프로젝트 설정의 버튼에 마우스를 올리면 동작 설명을 볼 수 있습니다.

**Run Project**는 자동 진행하고 **Debug Project**는 시작 위치에서 멈춥니다. Continue는 현재 PC에서 지정 간격으로 진행합니다. 실행 간격과 화면 갱신은 분리되어 있으며, 빠른 실행의 진행 화면은 최대 10Hz로 갱신합니다. 단계 실행·중단점·일시정지·종료 상태는 즉시 표시합니다. 기본 간격은 250ms이며, 도구 모음에서 간격을 고르거나 사용자 지정 값을 입력합니다. 프로젝트와 사용자 설정에 명시적으로 저장한 간격은 유지합니다. 명령 수와 실행 중 처리 속도도 표시합니다. 상태 표시줄의 시계 또는 **Set Auto Step Delay**에서 실행 중에도 간격을 바꿀 수 있습니다. `0ms`는 빠른 실행이고 Pause로 중단할 수 있습니다. 재개·재시작 시에도 같은 간격을 사용하며 설정을 저장합니다.

실행 뷰는 보조 사이드바에 기본 배치하며 사용자가 옮긴 위치를 기억합니다. 닫은 뒤에는 **UmJoonSIC: 실행 및 메모리 뷰 열기** 또는 **Show Memory**로 다시 열 수 있습니다. 레지스터의 HEX MODE로 16진수/10진수를 전환하고, 메모리는 주소·변수 이름 검색·이전/다음 페이지·변경 바이트 강조·Hex 복사를 제공합니다.

소스와 Listing은 일반 에디터처럼 분할하거나 다른 창으로 옮길 수 있습니다. 소스의 **Listing에서 보기**, Variables/Watch의 **메모리와 소스 보기**, 메모리 바이트의 더블클릭·Enter로 화면 사이를 이동합니다. **최근 저장 위치**는 실제 저장 명령이 쓴 주소를 표시하고, 실행 상태를 누르면 현재 PC로 이동합니다. 파일·탭 드래그, 저장·복구, 검색·Git은 VS Code 기본 기능을 사용합니다. Listing에서 행을 선택한 뒤 F12·Enter·**소스 열기**, 또는 행 더블클릭으로 소스 위치로 이동합니다. 실행 중에는 실행 시작 시점의 소스 스냅샷을 엽니다.

레지스터와 심볼은 Run and Debug의 Variables에 표시합니다. Watch에는 `A` 또는 `$A`, 심볼명, `SECTION::NAME`, `mem[0x1000,16]`처럼 입력합니다. 소스의 디버그 호버는 명령 문맥을 사용해 같은 이름의 변수와 레지스터를 구분합니다. 배열은 펼쳐 필요한 범위를 읽고 값은 signed 정수·hex·ASCII 또는 부동소수 값으로 표시합니다. 메모리 창은 hex/ASCII, 주소 이동, 변수 영역 아래의 이름·범위 표시, PC·변경 강조와 hex 복사를 제공합니다. 여러 행에 걸친 변수는 범위를 이어 표시하며, 겹치는 변수는 별도 줄로 구분합니다. 검색창에 `RESULT` 또는 `MAIN::RESULT`를 입력해 변수·라벨 위치로 이동합니다. 정확한 대소문자의 이름을 먼저 찾고, 없으면 대소문자를 구분하지 않고 찾습니다. 중복 이름은 섹션을 지정하며, `FACE` 같은 이름과 16진수 주소가 겹치면 `0xFACE`로 주소를 지정합니다. 절대 EQU 상수는 메모리 위치로 검색하지 않습니다.

디버거는 **실행을 시작할 때의 소스 버퍼 스냅샷**을 보여줍니다. 실행 중 원본을 고쳐도 실행 중인 코드가 바뀌지 않습니다. 새 코드를 실행하려면 Stop 후 다시 실행합니다. Restart는 기존 스냅샷을 새 CPU·메모리·파일 위치로 다시 실행합니다. 심볼릭 링크와 실제 파일 어느 쪽에 설정한 중단점도 같은 실행 소스에 연결됩니다.

## 여러 파일과 기존 프로젝트

`project.sic` 설정 화면의 **실행 파일**에서 asm 파일을 검색하거나 선택합니다. 탐색기에서 새로 만든 asm은 해당 프로젝트의 실행 목록에 자동으로 추가하며, 등록한 파일은 파란색 순번(1–99)으로 구분합니다. 100번째 이후이거나 여러 프로젝트에서 공유하는 파일은 S로 표시하며, 마우스를 올리면 프로젝트별 순번을 확인할 수 있습니다. 기존 파일은 우클릭으로 추가할 수 있습니다. 자동 등록은 `umjoonsic.autoAddNewAsmFiles`로 끌 수 있으며, 편집 중이거나 손상된 `.sic`은 자동으로 덮어쓰지 않습니다. 파일 목록의 드래그·Alt+↑/↓·위/아래 버튼과 **시작 프로그램**에서 입력 순서와 시작 섹션을 정합니다. 모드·간격·장치와 함께 루트 `.sic` 파일에 저장하며, 자동 감지 시 `launch.json`을 따로 만들지 않습니다.

탐색기에서 등록 파일을 삭제하거나 파일·폴더를 이동하면 프로젝트의 경로도 함께 갱신됩니다. 이름 변경은 연결된 파일 장치 경로에도 반영됩니다. 일반적인 파일 작업과 설정 변경은 함께 실행 취소·다시 실행할 수 있으며, 변경된 `.sic`를 저장한 뒤 실행합니다. 여러 파일 작업의 확인·미리보기가 겹쳐 설정 변경이 충돌하면 **프로젝트 경로 갱신**으로 현재 경로를 반영합니다. 이 복구는 별도의 실행 취소 단계이며, 직접 편집한 설정은 자동으로 덮어쓰지 않습니다. 다른 프로젝트 폴더로 파일을 옮겨도 원래 프로젝트의 등록과 순서를 유지합니다. 심볼릭 링크로 같은 파일을 가리키는 경로는 중복으로 추가하지 않으며, 직접 작성한 실행 목록에 같은 실파일이 두 번 있으면 실행 전에 알려줍니다.

루트에 `project.sic`이 있으면 우선 사용하고, 다른 이름의 `.sic` 파일 하나만 있으면 그 파일도 인식합니다. 루트에 여러 `.sic` 파일이 있고 `project.sic`은 없으면 임의로 고르지 않고 실행 시 오류를 표시합니다. 하위 폴더의 `.sic`은 해당 폴더를 프로젝트 루트로 열었을 때 인식합니다. 손상된 설정과 저장하지 않은 편집 내용은 덮어쓰지 않습니다.

`.sic` 파일은 기본적으로 설정 화면으로 열립니다. 실행 파일 경로와 Main 후보를 자동완성하고, Main 파일과 누락된 경로를 표시하며, 파일 선택·소스 순서 변경·장치 번호(0x00~0xFF) 연결을 지원합니다. **저장** 또는 Ctrl/Cmd+S로 반영하며, 실행 취소·다시 실행도 지원합니다. JSON이 손상되면 오류와 **텍스트로 열어 수정** 버튼을 표시합니다. 저장 방식은 VS Code의 `files.autoSave`를 따르며, 꺼져 있으면 Ctrl/Cmd+S로 저장합니다. 새 장치 파일 생성은 기존 파일을 덮어쓰지 않고, 설정의 실행 취소로 장치 파일에 쓴 데이터를 삭제하지 않습니다.

프로젝트의 상대경로는 `/`와 `\`를 모두 구분자로 읽습니다. 다른 운영체제의 절대경로와 드라이브를 생략한 Windows 루트 경로는 실행 전에 오류로 표시하므로 설정에서 파일을 다시 선택합니다. 파일명 자체에 `\`가 들어간 POSIX 파일은 선택 시 절대경로로 저장해 보존합니다.

프로젝트 파일 내부 형식:

기존 원본의 `SIC`, `SICXE`, `SIC/XE` 모드 표기도 대소문자에 관계없이 읽습니다. 파일을 여는 것만으로 내용을 다시 저장하지 않습니다.

```json
{
  "asm": ["main.asm", "routine.asm"],
  "mode": "sicxe",
  "main": "MAIN",
  "stepDelayMs": 500,
  "filedevices": [{ "index": 7, "filename": "input.dev" }]
}
```

프로젝트 파일 없이 고급 실행 구성을 사용하거나, 하위 폴더의 설정을 명시적으로 가져오는 기능도 제공합니다. 가져온 프로젝트는 전체 상대 경로로 구분해 같은 이름의 하위 폴더에서도 각각의 설정을 보존합니다. `.sic` 프로젝트의 파일 선택·순서·시작 프로그램·장치 설정 명령은 설정 편집기로 연결되며, Explorer의 파일 추가는 바로 목록에 반영합니다. 프로젝트가 없는 경우에는 `.vscode/launch.json`을 사용합니다. 기존 실행 구성의 파일 목록에는 등록된 외부 파일도 표시하며, 변경 사항은 원래의 전역·작업 영역·폴더 범위에 저장합니다. 같은 프로젝트를 다시 가져와도 `preLaunchTask` 등 별도로 작성한 실행 옵션은 유지합니다.

```json
{
  "type": "umjoonsic",
  "request": "launch",
  "name": "SIC XE 실습",
  "mode": "sicxe",
  "programs": ["${workspaceFolder}/main.asm", "${workspaceFolder}/routine.asm"],
  "mainSection": "MAIN",
  "stopOnEntry": true,
  "stepDelayMs": 500,
  "fileDevices": [{ "index": 7, "filename": "${workspaceFolder}/input.dev" }]
}
```

SIC는 각 프로그램의 절대 START 주소에 배치하고 크기가 있는 영역의 중첩을 거부합니다. 크기가 0인 프로그램은 메모리를 차지하지 않습니다. XE는 여러 파일이나 한 파일의 여러 CSECT를 링크합니다. XE 링크 입력은 시작 주소가 0인 재배치 가능한 section이어야 합니다. 단일 section은 0이 아닌 START도 지원합니다. object 형식이 절대 상수의 속성을 보존하지 못하므로 절대 EQU의 EXTDEF는 진단으로 거부합니다. 내부 절대 EQU와 상대 심볼의 EXTDEF는 사용할 수 있습니다. 링크로 섹션이 이동할 때 절대값과 PC 또는 BASE의 재배치 성질이 달라 값이 변하는 명령은 해당 위치에 오류를 표시합니다. 이런 경우 format 4 명령이나 재배치 성질이 맞는 BASE 식을 사용합니다. format 4도 링크 후 주소가 20비트 범위(0~0xFFFFF)를 벗어나면 해당 소스 명령에 오류를 표시하고 산출물을 만들지 않습니다.

HEX 데이터 `X'...'`와 문자열의 `\xHH` escape는 ASCII 16진수 숫자만 허용합니다. 대소문자는 구분하지 않으며 부호나 전각 문자는 해당 소스 위치에 오류로 표시합니다.

XE의 단항 `+`·`-`는 곱셈·나눗셈보다 먼저 적용합니다. `END`의 실행 주소가 메모리 범위를 벗어나면 편집 중에도 해당 피연산자에 오류를 표시합니다.

XE 표현식 뒤에 연산자 없이 값이나 심볼이 더 나오면 해당 토큰에 오류를 표시합니다. 중간 계산이 32비트 정수 범위를 넘으면 해당 연산자에 오류를 표시합니다. 최종 수학적 결과가 범위 안이어도 중간 계산이 넘치는 식은 허용하지 않으며, 실행 중 레지스터의 24비트 산술 규칙은 유지합니다.

## 파일 장치

프로젝트 설정의 **파일 장치**에는 소스에서 확인한 RD·WD·TD 장치 번호와 연결된 파일이 함께 표시됩니다. 기존 파일 연결·새 파일 생성·파일 열기를 지원합니다. WORD의 첫 바이트와 BYTE의 값은 구분하며, 실행 시 결정되는 주소를 임의의 장치 번호로 추정하지 않습니다. `.sic` 프로젝트에서 **Configure File Devices**도 같은 설정 화면을 엽니다. RD·WD·TD가 이 파일을 사용합니다. 기본 0/1/2를 터미널 표준 입출력으로 연결하지 않습니다.

보조 사이드바의 **장치** 패널에서 실제 읽은 바이트·쓴 바이트·미연결 장치에 버려진 출력을 문자 또는 Hex로 확인하고 복사합니다. EOF와 다음 입력 바이트의 커서도 표시합니다. 제어 문자는 숨기지 않고 표시하며, 각 방향의 최근 8KiB가 화면과 복사 대상입니다. 중지 후에도 장치별 마지막 표시 범위를 확인할 수 있습니다.

파일 장치는 읽기·쓰기 위치를 공유합니다. WD는 현재 위치를 덮어쓰고 파일을 자동으로 비우거나 끝에 추가하지 않습니다. EOF는 0으로 보입니다. Restart는 파일을 닫고 위치를 처음으로 되돌리지만 **이미 쓴 파일 내용을 복구하지는 않습니다**. 실행 설정의 변경은 다음 새 실행에 적용됩니다. **파일 비우기**는 일시정지 후 파일명과 연결 장치 목록을 확인한 경우에만 내용을 삭제합니다. 같은 파일을 공유하는 장치의 커서와 기록도 함께 초기화됩니다. 실행 중 열린 장치의 파일 경로가 삭제·교체되었거나 파일의 동일성을 확인할 수 없으면 내용을 비우지 않고 오류를 표시합니다. 파일 연결을 확인하고 새로 실행한 뒤 다시 시도합니다. 파일 동일성 정보를 제공하지 않는 파일 시스템에서는 파일 비우기를 사용할 수 없으며, 일반 입출력과 미리보기는 유지됩니다.

## 편집 기능

- SIC 26개·XE 59개 명령과 모드별 지시어 자동완성, format 4·레지스터·숫자·심볼 문맥 구분
- 명령의 opcode·형식·피연산자 설명과 원본 VM 미지원 명령 안내
- 편집 중 미저장 버퍼의 오류를 Problems와 소스 밑줄로 표시
- CSECT 범위를 지키는 현재 문서의 정의 이동·Outline
- Space로 열 맞춤, Tab·Shift+Tab으로 필드 이동, Enter로 명령어 열에서 새 줄 시작, 주석 중간 Enter는 다음 줄에도 주석을 유지, 열 끝의 자동 공백은 Backspace로 한 번에 제거
- **Format Document**와 붙여넣기 정렬에서 줄 번호·전체 들여쓰기·소문자 명령어를 정리하고 명확한 설명 주석에 점을 붙입니다. 문자열·기존 유효 코드의 의미·개행은 보존하며, 모호한 추가 피연산자의 오류를 주석으로 숨기지 않습니다. 자동완성·스니펫·여러 커서의 기본 편집도 유지합니다.
- `sic-program`, `sic-loop`, `sic-subroutine` 스니펫

입력 정렬은 `[umjoonsic]`의 `editor.formatOnType`, 붙여넣기 정렬은 `editor.formatOnPaste`로 끌 수 있습니다.

모드 기본값은 SIC입니다. 실행 구성의 mode가 있으면 그 실행에서는 우선합니다. 실행 소스 스냅샷은 다른 디버거를 선택하거나 실행을 끝낸 뒤에도 원래 모드를 유지합니다. 문서 버전과 모드가 같으면 언어 분석 결과를 재사용합니다. SIC의 `START 1000`은 16진수, XE에서는 10진수입니다.

## 지원 범위

- 한 확장 호스트에서 SIC 디버깅 세션 하나를 지원합니다. 서로 다른 VS Code 창은 별도 엔진으로 실행됩니다.
- 가상 파일 시스템과 Restricted Mode에서는 편집 기능만 제공합니다. 어셈블·실행·파일 장치에는 신뢰된 로컬/Remote 파일 시스템과 Java가 필요합니다.
- 조건부·데이터 중단점, 역방향 실행, 임의 표현식 계산, 레지스터·메모리 직접 쓰기는 제공하지 않습니다. 호출 스택에는 정확한 현재 PC 프레임을 표시합니다.
- `NORM SIO HIO TIO SVC LPS STI SSK`는 기존 엔진의 미구현 명령으로 명확한 실행 오류를 반환합니다.
- 기존 엔진의 immediate 값 해석과 double 상위 48-bit 부동소수 표현을 유지합니다. 교재의 모든 수치 규격을 인증한 구현은 아닙니다.

## 개발과 빌드

개발에는 Node.js 22 이상과 JDK 17 이상을 사용합니다. 첫 빌드는 checksum을 고정한 Gson을 내려받고, 생성한 JAR를 VSIX에 포함합니다. 설치 후 Java 엔진 JAR는 별도로 내려받지 않습니다. Java가 없는 환경의 JRE 준비만 네트워크를 사용합니다.

```sh
npm ci
npm run package
```

패키징은 엔진과 TypeScript를 함께 빌드합니다. JDK 경로는 `UMJOONSIC_JAVAC`으로 지정할 수 있습니다. CI는 세 운영체제에서 패키징·TypeScript 검사를 수행합니다.

## 자동 빌드와 릴리스

`develop`에서 작업하고 `main`으로 병합합니다. 두 브랜치의 push와 대상 PR에서 Linux·Windows·macOS 빌드를 확인하며, Actions 실행의 `vsix` 아티팩트에서 설치 파일을 받을 수 있습니다.

`main`에 변경이 반영되면 패치 버전을 자동 증가시킵니다. 현재 기준 버전이 `1.7.6`이고 태그가 없으면 첫 릴리스는 `v1.7.7`, 다음은 `v1.7.8`입니다. 세 운영체제의 빌드가 모두 성공한 뒤 해당 커밋에 태그를 만들고, 공통 VSIX와 자동 생성한 변경 내역을 GitHub Release로 배포합니다. `main`에 직접 push한 경우에도 같은 절차가 실행됩니다.

실제 배포 버전은 Git 태그를 기준으로 관리합니다. 빌드 중에만 `package.json`과 lockfile에 배포 버전을 적용하며, 소스의 버전은 최초 기준값으로 유지합니다. 같은 커밋을 재실행하면 기존 태그를 재사용하고, 업로드 실패로 남은 초안은 재시도합니다. 이미 배포한 VSIX는 덮어쓰지 않습니다. 더 최신이거나 서로 갈라진 커밋이 먼저 태그된 경우에는 이전 커밋의 새 릴리스를 차단합니다.

배포 실행은 순차 처리하며, 실패한 작업은 Actions에서 **Re-run all jobs**로 재시도할 수 있습니다. Actions의 **Run workflow**를 `main`에서 실행해도 같은 배포 절차가 적용됩니다. 기본 `GITHUB_TOKEN`을 사용하므로 별도 배포 토큰은 필요하지 않습니다.
